## librouting v1.5.0 — BGP OTC leak-detection attribute in the filter DSL

librouting 1.5.0 ships the RFC 9234 §3.1 OTC ("Only To Customer")
attribute in the filter DSL (ROADMAP "Per-protocol route attributes
and an external conversion corpus"). The filter DSL now exposes
`bgp.otc` so an operator can write the canonical leak-detection
idiom directly. The new `RouteFieldKind::BgpOtc` variant is a
breaking change for downstream `match` exhaustiveness, so the bump
is minor per [`docs/RELEASE-PLAN.md`](../RELEASE-PLAN.md) §1; the
C ABI surface is unchanged.

### New features

**BGP OTC filter DSL surface** (`bgp`, `policy`, `cli`). The filter
DSL now exposes the RFC 9234 §3.1 OTC attribute as `bgp.otc`
(read-only `Int`, `0` when absent or set to zero), so an operator
can write the canonical leak-detection idiom directly:

- `if bgp.otc != 0 then reject;` — RFC 9234 §5 egress rule 2 in
  filter form: a route that already carries OTC is "customer-only"
  and must not transit to a provider or peer.
- `if defined(bgp.otc) && bgp.otc != 0 then reject;` — the
  `defined()` gate distinguishes "absent" from "set to zero" so a
  peer that legitimately set OTC=0 (rare but legal) does not trip
  the leak detector.

`lr-bgp::path::PathAttributes` gains typed `otc()` and `has_otc()`
accessors; the former returns `Option<Otc>` (`None` on absent or
malformed, `Some(Otc(0))` on "set but zero"), the latter reports
physical presence so `defined(bgp.otc)` keeps the two cases
distinct. `lr-policy::bgp` carries matching `otc()` and `has_otc()`
helpers that read by tag from `Route.attributes` via
`Attributes::get_u32_be` (the same in-place u32 fast path
`bgp.local_pref` and `bgp.med` use — no `Vec<u8>` clone). The
filter DSL's peephole pass fuses `bgp.otc` integer comparisons into
`BranchFieldIntCmp` (the same fast path the other int-typed fields
use), so `if bgp.otc != 0 then …` pays no `Value::Int` allocation.

The BIRD filter translator renames `bgp_otc` to `bgp.otc`. A new
corpus case `tests/corpus/bird/bgp-otc-leak-filter.conf` exercises
both the leak-detection idiom and the `defined()` distinction. A
proptest strategy in `lr-bgp::role::otc` pins the `Otc::decode`
contract for the filter DSL surface (4-byte input accepted,
byte-exact round-trip, no input panics).

### Compatibility

**Breaking change (Rust API).** The new `RouteFieldKind::BgpOtc`
variant is a breaking change for downstream `match` exhaustiveness
— a downstream `match` on `RouteFieldKind` that lacks a wildcard
will fail to compile. Per `docs/RELEASE-PLAN.md` §1 and the
v1.3.0 / v1.4.0 precedent, this ships as a minor bump. The
`api-surface` CI gate (`cargo semver-checks`) catches the
accidental kind that slips past review.

**No C ABI change.** No new `lr_*` symbols, `ABI_VERSION` stays at
2, `lr_filter_context_t` is untouched. The new `FilterContext`
trait methods (`bgp_otc`, `bgp_has_otc`) carry default
implementations that delegate to `lr_policy::bgp`, so every
existing embedder — daemon, FFI built-in, FFI callback-table,
benches, test stubs — inherits the correct behaviour without
recompiling.

**BIRD compatibility.** `bgp_otc` filters translate to `bgp.otc`
with no semantic shim (both are integers, `0` = absent or set to
zero). `defined(bgp_otc)` survives verbatim — `defined()` shares
spelling between BIRD and lr.
