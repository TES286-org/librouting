# FFI design — `lr-ffi`

Read this before adding an entry point to `crates/lr-ffi`, or before
embedding the library from C and needing to know why the ABI is shaped
the way it is. The embedder-facing guides are [`bindings/c.md`](bindings/c.md),
[`bindings/cpp.md`](bindings/cpp.md), [`bindings/go.md`](bindings/go.md)
and [`bindings/python.md`](bindings/python.md); this page is the design
rationale behind them.

The source of truth is [`crates/lr-ffi/src/`](../crates/lr-ffi/src/) and
the header it generates, [`include/lr_ffi.h`](../include/lr_ffi.h).

## 1. Layering

`lr-ffi` is a thin `extern "C"` wrapper over the Rust crates. It owns no
protocol state: every entry point locks the underlying `DefaultRouter`
(or a dedicated handle) and delegates to the library.

```text
+-----------------------------+
| C / C++ / Go / Python       |
| embedder                    |
+--------------+--------------+
               | extern "C"
+--------------v--------------+
| lr-ffi                      |
| panic barrier, handle       |
| types, cbindgen header      |
+--------------+--------------+
               | Rust calls
+--------------v--------------+
| lr-router, lr-bgp, lr-ospf, |
| lr-babel, lr-policy,        |
| lr-mpls, lr-srv6, lr-core   |
+-----------------------------+
```

[`crates/lr-ffi/Cargo.toml`](../crates/lr-ffi/Cargo.toml) sets
`crate-type = ["cdylib", "staticlib", "rlib"]`. The `cdylib` produces
`liblr_ffi.so` / `lr_ffi.dll` / `liblr_ffi.dylib` for dynamic linking,
the `staticlib` produces `liblr_ffi.a`, and the `rlib` lets another Rust
crate use the handle types without going through the C ABI.

## 2. The panic barrier

**Contract: a Rust panic never unwinds across the C ABI.** C does not
understand Rust unwinding, so a panic that reaches a C frame is
undefined behaviour under `extern "C"`.

Every entry point wraps its body in `guarded`
([`crates/lr-ffi/src/lib.rs`](../crates/lr-ffi/src/lib.rs)), which runs
the body inside `catch_unwind` with `AssertUnwindSafe` and returns a
fallback when the body panics. On a caught panic:

1. `set_last_error` records `"panic caught in FFI"` in the thread-local
   last-error string.
2. The entry point returns its documented panic value:
   - `-4` for `int32_t` and `int64_t` returns.
   - `NULL` for pointer returns, such as `lr_router_new`.
   - `0` for `usize` and `u32` returns.
   - nothing for `void` returns.

`LR_ERR_PANIC` in [`crates/lr-ffi/src/error.rs`](../crates/lr-ffi/src/error.rs)
is the Rust name for `-4`. It is a Rust `pub const`, not a macro in the C
header — see §4.

### What the barrier does not catch

- **A library error.** A `Result::Err` is an ordinary return value, not a
  panic. The entry point maps it to a negative code and sets the
  last-error string to the `Display` form of the error.
- **A deadlock.** `Mutex::lock` blocks under contention; it does not
  panic and the barrier cannot interrupt it.
- **`abort`, `SIGFPE` and stack overflow.** `catch_unwind` catches
  unwinding panics only. `[profile.release] panic = "abort"` in
  [`Cargo.toml`](../Cargo.toml) means a panic in a release build
  terminates the process. `[profile.dev]` leaves the default `unwind`,
  so the barrier is what `cargo test` exercises.

`cargo test -p lr-ffi` exercises the barrier directly. The C and C++
harnesses in `tests/ffi/` exercise the compiled surface in the
`ffi-bindings` job of [`.github/workflows/ci.yml`](../.github/workflows/ci.yml).

## 3. The `lr_bytes_t` ownership model

**Contract: every `lr_bytes_t` an entry point fills is owned by the
caller and is released with `lr_bytes_free`.**

`lr_bytes_t` is a `#[repr(C)]` struct mirroring a `Vec<u8>`:

```c
typedef struct lr_bytes_t {
    uint8_t *ptr;
    uintptr_t len;
    uintptr_t cap;
} lr_bytes_t;
```

`lr_bytes_t::from_vec` `std::mem::forget`s the `Vec` and hands the
embedder `ptr`, `len` and `cap`. `lr_bytes_free` reconstructs the `Vec`
from all three fields and drops it
([`crates/lr-ffi/src/handle.rs`](../crates/lr-ffi/src/handle.rs)).

Rules for the embedder:

1. **Never `free` the `ptr`.** `lr_bytes_free` needs `cap` to release the
   allocation correctly.
2. **Read the return code before reading the struct.** An entry point
   signals failure with a negative return code; the `lr_bytes_t` it was
   given may be untouched.
3. **Free the bytes once you have copied what you need.** They do not
   point into the router, so holding them is not itself unsafe, but the
   copies add up.
4. **A NULL `lr_bytes_t *` is valid input** to `lr_bytes_free`,
   `lr_bytes_len` and `lr_bytes_ptr`.
5. **The pointer is valid until `lr_bytes_free`.** A second free is a
   double free.

The C++ wrapper, the Go binding and the Python binding free the buffer
for you; `crates/lr-ffi/src/handle.rs` is the reference implementation
of the convention.

## 4. The cbindgen pipeline

**Contract: `include/lr_ffi.h` is generated by `cbindgen` from
[`crates/lr-ffi/build.rs`](../crates/lr-ffi/build.rs).** Do not edit the
header by hand; the next `cargo build -p lr-ffi` overwrites it.

The pipeline:

1. `cargo build -p lr-ffi` runs `build.rs`.
2. `build.rs` builds a `cbindgen::Config`:
   - `language: C`. C++ consumers include the same header, wrapped in
     `extern "C"` by [`include/librouting.hpp`](../include/librouting.hpp).
   - `include_guard: "LR_FFI_H"`.
   - `export.exclude` for `LrError` and `lr_error_t`. cbindgen emits
     `LrError` as a C23 fixed-width enum whose pre-C23 fallback
     (`typedef int32_t LrError`) conflicts with the enum definition. No
     entry point uses the type — they return plain `int32_t` — so the
     exclusion keeps the header portable.
   - `after_includes`: the `#define` blocks for `LR_PROTO_*`,
     `LR_METRIC_*`, `LR_EVENT_*` and `LR_MAX_PREFIX_*`. cbindgen cannot
     derive those from Rust `pub const` values.
3. `cbindgen::generate_with_config` parses the Rust AST and writes the
   header.
4. When `DOCS_RS` is set, `build.rs` returns before writing: the docs.rs
   filesystem is read-only and the header is not needed there.

If cbindgen fails, `build.rs` prints `cargo:warning=cbindgen failed: …`
and the build continues against the header already on disk.

### What the header does not define

`after_includes` defines the `LR_PROTO_*`, `LR_METRIC_*`, `LR_EVENT_*`
and `LR_MAX_PREFIX_*` blocks and nothing else. The header has **no
`LR_ERR_*` macro** and **no `LR_ABI_VERSION` macro**, although its doc
comments refer to `LR_ERR_PANIC`. Error values reach C as `int32_t`
return codes plus `lr_last_error()`; §10 gives the convention and
[`crates/lr-ffi/src/error.rs`](../crates/lr-ffi/src/error.rs) names the
values on the Rust side.

## 5. The opaque-handle pattern

Every Rust object exposed to C is an opaque handle: a `#[repr(C)]` struct
whose only field is `_private: [u8; 0]`, behind a
`pub type lr_*_t = *mut Opaque*` alias. C sees a forward declaration, so
it can hold the pointer but never dereference it.

```rust
#[repr(C)]
pub struct OpaqueRouter {
    _private: [u8; 0],
}
pub type lr_router_t = *mut OpaqueRouter;
```

`box_router` boxes a `Mutex<DefaultRouter>` and returns the raw pointer;
`unbox_router` rebuilds the `Box` and drops it
([`crates/lr-ffi/src/handle.rs`](../crates/lr-ffi/src/handle.rs)).

Opaque handles buy two things. The C side never depends on a struct
layout, so adding a field to `DefaultRouter` cannot break the ABI. And
every mutation goes through an entry point that takes the lock and runs
the panic barrier, so the C side cannot reach the internals at all.

### The handle zoo

| Handle | Rust payload | Synchronisation |
| --- | --- | --- |
| `lr_router_t` | `Box<Mutex<DefaultRouter>>` | `Mutex` |
| `lr_roa_store_t` | `Box<lr_bgp::RoaStore>` | none |
| `lr_damping_t` | `Box<Arc<Mutex<DampingTable>>>` | `Arc<Mutex>` |
| `lr_route_t` | `Box<Route>` | none |
| `lr_prefix_list_t` | `Box<PrefixList>` | none |
| `lr_route_map_t` | `Box<RouteMap>` | none |
| `lr_resolver_t` | `Box<PolicySet>` | none |
| `lr_filter_t` | `Box<CompiledFilter>` | none |

`lr_router_t` wraps a `Mutex` because the router is the shared state every
entry point touches. `lr_roa_store_t` needs no lock: `RoaStore` is
already `Send + Sync`, and validation reads a read-locked `Arc` snapshot.
The policy objects are single-threaded by construction — the embedder
builds one, hands it to the router or evaluates it, and does not share it.

### The destroy contract

`lr_router_destroy` and every other `lr_*_free` / `lr_*_destroy`:

1. **Must not run concurrently with any other call on the same handle.**
   The `Mutex` is not reentrant, and a destroy that overlaps a call in
   flight is a use-after-free.
2. **Must not be called from a thread that holds the handle's lock** — for
   example from a hook or sink that runs under `lock_router`.
3. **Must not be called twice.** A double destroy is a double free.

`unbox_router` documents the contract; nothing in the FFI layer enforces
it, so the obligation is the one `free(3)` puts on a C program.
`lr_router_destroy` does not drain or flush: it drops the boxed `Mutex`
with all session state, RIBs and queued output. An embedder that needs a
graceful teardown drains and ticks first
([`crates/lr-ffi/src/handle.rs`](../crates/lr-ffi/src/handle.rs)).

## 6. The non-reentrant lock hazard

Every `lr_router_*` entry point holds the `Mutex<DefaultRouter>` for the
whole call, including while import and export hooks run and while the BMP
sink writes. `std::sync::Mutex` is **not reentrant**, so a hook that
calls _any_ `lr_router_*` function for the same router on the same thread
deadlocks on the second acquisition.

The rule for hook authors:

> Never call back into the FFI from code that runs under the router
> lock. Collect the work you need and call back only after the entry
> point returns.

The daemon's own hooks follow this rule: they read route attributes
through the `FilterContext` trait rather than through the FFI. An
embedder that needs to override individual accessors uses the
`lr_filter_context_t` callback table, whose callbacks run under the same
lock and must not re-enter it either.

A panic while the lock is held poisons the mutex. From then on
`lock_router` returns `None` and every entry point on that router fails.
The barrier in §2 prevents most panics from reaching that state, but a
panic that originates outside Rust cannot be recovered from — treat the
handle as poisoned. `lock_router` carries the full note
([`crates/lr-ffi/src/handle.rs`](../crates/lr-ffi/src/handle.rs)).

## 7. The embedder main loop

The library performs no I/O. The embedder owns the transport and the
clock, and drives each session with three calls:

| Call | What it does |
| --- | --- |
| `lr_router_feed_input` | Inbound bytes from the peer into the session |
| `lr_router_drain_output` | Bytes the session wants sent to the peer |
| `lr_router_tick` | Advance the router clock to `now_ms` |

```c
/* now_ms comes from your monotonic millisecond clock. */
for (;;) {
    lr_router_tick(r, monotonic_ms());

    /* Drain until empty: one lr_bytes_t per call, freed after sending. */
    lr_bytes_t out = {0};
    if (lr_router_drain_output(r, session, &out) == 0) {
        send_to_peer(session, lr_bytes_ptr(&out), lr_bytes_len(&out));
    }
    lr_bytes_free(&out);

    /* React to router events. */
    lr_event_t events[16];
    int32_t n = lr_router_poll_events(r, events, 16);
    for (int32_t i = 0; i < n; i++) {
        handle_event(&events[i]);
    }

    /* Your transport: call lr_router_feed_input for each read. */
    poll_transports(r);
}
```

- **One clock.** `lr_router_tick` takes milliseconds; `lr_damping_decay`
  takes seconds. Convert from a single monotonic source.
- **Drain until empty** before sleeping, so nothing waits for the next
  wake-up.
- **`lr_router_poll_events` requeues what did not fit** and returns the
  number of events written, so a small buffer loses nothing. Transport
  events never surface: outgoing bytes ride `lr_router_drain_output` and
  timers are internal.
- **`lr_router_start_session` starts the protocol FSM** once the
  transport is connected. Nothing reaches the wire before that call.

## 8. Thread safety, per handle

| Handle | Concurrency |
| --- | --- |
| `lr_router_t` | Calls serialise on the internal `Mutex`; the lock is not reentrant (§6) and destroy must not overlap |
| `lr_roa_store_t` | `Send + Sync`; validation reads a snapshot and never blocks a writer |
| `lr_damping_t` | `Arc<Mutex<DampingTable>>` shared with the import hook, so decay may run on another thread |
| Policy objects | No lock; build and use on one thread at a time |

Two consequences matter to an embedder.

An `lr_router_t` is safe to call from several threads in the sense that
the calls serialise rather than corrupt each other, but the deadlock and
destroy rules in §5 and §6 mean the practical design is one thread per
router. `lr_damping_decay` is the exception worth using from a second
thread: the damping table is behind its own `Arc<Mutex>`, and destroying
the handle releases only the embedder's reference while the hook keeps
its own.

The last-error string is thread-local
([`crates/lr-ffi/src/error.rs`](../crates/lr-ffi/src/error.rs)), so
`lr_last_error()` reports the most recent failure on the calling thread
and never a failure from another thread.

## 9. What is not exposed, and why

### The OSPF and Babel engines

`lr_router_add_ospf_session`, `lr_router_add_ospfv3_session`,
`lr_router_add_ospf_session_ext` and `lr_router_add_babel_session` are
exposed. Each builds a `SessionConfig` and hands it to the router, which
is the path the daemon takes. The engines are not exposed: the I/O loops
are daemon-driven, because the daemon owns the sockets, the timers and
the thread. An entry point for an engine would advertise a capability the
library does not have, since an embedder cannot run one without also
writing the daemon's loop.

### LDP

There is no LDP entry point. `lr-router` has no LDP session kind — the
LDP engine is daemon-driven, over UDP/TCP discovery and transport — so a
session-creation call would advertise a capability the library does not
have.

### BMP, BFD and MRT

`lr-ffi` does not depend on `lr-bmp`, `lr-bfd` or `lr-mrt`
([`crates/lr-ffi/Cargo.toml`](../crates/lr-ffi/Cargo.toml)), so none of
those codecs is reachable through the C ABI. The daemon is their only
consumer.

The codec entry points that _are_ exported are `lr_bgp_decode`,
`lr_ospf_decode_v2`, `lr_babel_decode`, the `lr_bgp_encode_*` family, and
`lr_srv6_encode_srh` / `lr_srv6_decode_srh`. Read
[`include/lr_ffi.h`](../include/lr_ffi.h) for the current list rather
than a list copied here.

### The exchange-plane prototype

The daemon's `exchange-plane` feature
([`crates/lr-cli/Cargo.toml`](../crates/lr-cli/Cargo.toml)) is
experimental and its wire format rides IANA experimental code points, so
the ABI does not expose it. It is daemon-only by design. See
[`research/EXCHANGE-PLANE.md`](research/EXCHANGE-PLANE.md).

## 10. The error model

Every entry point returns `int32_t` or `int64_t`: `0` on success and a
negative value on failure. A handful of calls use a positive result that
is not a failure — `lr_router_withdraw_v4` and `lr_router_uninstall_static_v4`
return `1` when the prefix was not locally originated or was not static,
`lr_router_request_route_refresh` returns `1` when a refresh was queued,
and `lr_damping_decay` and `lr_router_soft_reconfig_inbound` return a
count.

Read the return code first, then `lr_last_error()` for the text:

```c
uint64_t session = 0;
if (lr_router_add_bgp_session(r, 64512, 64513, bid, 90, 0, 1, &session) != 0) {
    fprintf(stderr, "add_bgp_session: %s\n", lr_last_error());
    return 1;
}
```

`lr_last_error()` returns a NUL-terminated UTF-8 string that is valid
until the next FFI call on the same thread — copy it if you need to keep
it. It is empty when no call has failed on that thread.

`crates/lr-ffi/src/error.rs` names the values on the Rust side:

| Value | `LrError` variant |
| --- | --- |
| `0` | `Ok` |
| `-1` | `Null` |
| `-2` | `InvalidHandle` |
| `-3` | `BadUtf8` |
| `-4` | `Panic` |
| `-5` | `AbiMismatch` |
| `-6` | `Other` |

The enum is not exported to C: the header excludes it (§4) and defines no
`LR_ERR_*` macro. A C caller compares against the codes documented on the
entry point it calls. Some of the names do not describe the practice:

- **`-3`** is also the documented code for a malformed argument on many
  entry points, not only for a string that was not valid UTF-8.
- **`-5`** is not an ABI-mismatch signal. `LrError::AbiMismatch` is
  declared but no entry point returns it when versions disagree. The two
  SRv6 entry points use the bare literal `-5` for an SRH encode or decode
  error, which their doc comments in the header state
  ([`crates/lr-ffi/src/srv6.rs`](../crates/lr-ffi/src/srv6.rs)).

### Checking the ABI version

`lr_abi_version()` returns `lr_core::ABI_VERSION`
([`crates/lr-core/src/lib.rs`](../crates/lr-core/src/lib.rs)). There is no
`LR_ABI_VERSION` macro in the header and no entry point performs a
compatibility check, so an embedder that cares calls `lr_abi_version()`
at startup and compares it against the value it compiled the header
from. A mismatch means the loaded shared library was built from different
source than the header.
